# FSDL Day 1 - ML 프로젝트 전략과 기획

## 체크포인트 답변

### Chapter 0

#### 1. 모델 배포(FastAPI/Streamlit)와 Full Stack DL, 그리고 MLOps는 각각 어떤 범위를 담당하며, 왜 세 과정이 분리되어야 하는지 설명할 수 있으신가요?

**답변:** 모델 배포는 학습된 모델을 API나 화면으로 호출 가능하게 만드는 단계다. Full Stack DL은 사용자 문제, 데이터 수집, 제품 설계, 운영까지 모델이 포함된 제품 전체를 다룬다. MLOps는 재현 가능한 학습·배포·모니터링·재학습 체계를 자동화하는 역할이다. 배포 기술만으로는 좋은 제품을 보장할 수 없고, 제품 기획과 안정적인 운영에는 별도 역량이 필요하므로 세 범위를 구분해 학습한다.

#### 2. "평평한 지구 ML"과 "둥근 지구 ML"의 차이를 동료에게 30초 안에 설명할 수 있으신가요? 데이터 플라이휠은 이 비유에서 어디에 해당하나요?

**답변:** 평평한 지구 ML은 고정된 데이터셋에서 모델 정확도를 높이는 데 집중한다. 둥근 지구 ML은 실제 사용자와 환경의 변화까지 포함해, 배포 뒤에도 데이터를 수집하고 모델을 개선하는 제품 관점이다. 데이터 플라이휠은 사용자 사용 → 데이터·피드백 축적 → 모델 개선 → 더 좋은 경험 → 사용 증가의 순환 구조에 해당한다.

#### 3. ML Powered Product와 MLOps의 지향점 차이를 구체적인 질문 하나씩으로 대비할 수 있으신가요?

**답변:** ML Powered Product는 “학습자가 실제로 더 빨리 이해하고 문제를 해결하게 하려면 어떤 기능이 필요한가?”를 묻는다. MLOps는 “그 기능의 모델을 어떻게 재현 가능하게 배포하고, 성능 저하를 감지해 안전하게 개선할 것인가?”를 묻는다. 전자는 사용자 가치, 후자는 운영 신뢰성이 중심이다.

### Chapter 1

#### 1. Software 1.0과 Software 2.0의 근본적인 차이는 무엇이며, 이 차이가 왜 전혀 다른 개발·테스트·운영 전략을 요구하는지 설명할 수 있으신가요?

**답변:** Software 1.0은 사람이 규칙을 코드로 직접 작성하고, Software 2.0은 데이터와 학습 알고리즘이 모델의 동작을 만든다. 따라서 Software 2.0은 코드 테스트만으로 충분하지 않고 데이터 품질, 모델 지표, 편향, 배포 후 성능 변화를 함께 검증하고 운영해야 한다.

#### 2. CACE 현상(Changing Anything Changes Everything)이 전통적인 소프트웨어에서는 왜 덜 문제가 되고, ML 시스템에서는 왜 치명적인지 정리해 보셨나요?

**답변:** 전통 소프트웨어는 입력과 규칙의 관계가 비교적 명시적이어서 변경 범위를 추적하기 쉽다. ML에서는 데이터 전처리, 라벨 기준, 특성, 모델, 사용자 행동 중 하나만 바뀌어도 모델 전체 성능과 예측 분포가 달라질 수 있다. 그래서 변경 이력, 데이터·모델 버전, 실험 기록과 모니터링이 필수다.

#### 3. "기술의 범용화(Commoditization)"가 ML 엔지니어의 역할을 어떻게 변화시키고 있는지 자신의 언어로 설명할 수 있으신가요?

**답변:** 좋은 모델과 API를 쉽게 사용할 수 있게 되면서, 모델을 처음부터 만드는 능력만으로 차별화하기는 어려워졌다. ML 엔지니어는 문제 정의, 데이터 품질, 적절한 Build/Buy/API 선택, 사용자 경험, 비용과 운영까지 연결하는 역할로 넓어지고 있다.

### Chapter 2

#### 1. 현재 구상하고 계신 (혹은 관심 있는) ML 프로젝트를 실현 가능성 × 임팩트 매트릭스에 배치해 보셨나요? 어느 사분면에 위치하나요?

**답변:** RAG 기반 학습 Q&A 도우미는 공개 학습 자료와 상용 LLM API를 이용할 수 있어 실현 가능성은 높다. 학습자의 탐색 시간과 질문 장벽을 낮출 수 있어 임팩트도 중간 이상이다. 따라서 초기 PoC는 ‘높은 실현 가능성 × 높은 임팩트’ 사분면에 둔다. 다만 답변 정확성과 출처 신뢰성은 검증해야 한다.

#### 2. Build vs. Buy vs. API 의사결정 트리에서, "API로 충분한가?"라는 질문에 답하기 위해 구체적으로 무엇을 확인해야 하는지 정리할 수 있으신가요?

**답변:** 목표 품질을 API 모델이 충족하는지, 문서·개인정보를 외부로 보내도 되는지, 호출 비용과 지연 시간이 허용 범위인지, 트래픽 증가 시 비용 예측이 가능한지, 모델·정책 변경에 대한 의존성이 감당 가능한지를 확인한다. 이 조건을 만족하면 PoC는 API로 시작하는 것이 빠르다.

#### 3. ML을 도입하기 전에 시도해야 할 4가지 대안을 나열하고, 각각이 더 적합한 상황을 예시와 함께 설명할 수 있으신가요?

**답변:** 첫째, 규칙 기반은 답변 유형이 정해진 FAQ처럼 규칙이 명확할 때 적합하다. 둘째, 사람 검토(Human-in-the-loop)는 오답 비용이 큰 상담·평가에서 적합하다. 셋째, Foundation Model API는 빠른 검증이 필요한 챗봇 PoC에 적합하다. 넷째, 전통 통계·간단한 ML은 수요 예측처럼 구조화된 데이터와 설명 가능성이 중요한 문제에 적합하다.

### Chapter 3

#### 1. ML 프로젝트 라이프사이클 4단계를 순서대로 말할 수 있으신가요? 각 단계의 핵심 활동을 한 문장으로 요약해 보세요.

**답변:** 1) 기획: 해결할 사용자 문제와 성공 지표를 정의한다. 2) 데이터: 수집·라벨링·정제와 데이터 품질 검증을 수행한다. 3) 모델 개발: 기준선부터 실험해 모델을 평가한다. 4) 배포·운영: 서비스에 연결하고 성능·비용·드리프트를 관찰하며 개선한다.

#### 2. "4단계 → 2단계 되돌아감"이 가장 흔한 이유는 무엇이며, 이를 미리 방지하기 위해 기획 단계에서 어떤 질문을 던져야 하는지 생각해 보셨나요?

**답변:** 배포 뒤 실제 입력이 학습 데이터와 다르거나, 필요한 라벨·문서·피드백이 부족한 사실을 발견하기 때문이다. 기획 단계에서 “실서비스 입력은 무엇인가?”, “정답과 피드백을 어떻게 얻는가?”, “실패 사례를 누가 검토하는가?”, “재학습에 쓸 데이터를 저장하는가?”를 미리 물어야 한다.

#### 3. 데이터 플라이휠이 자연스럽게 형성되는 제품과 인위적으로 설계해야 하는 제품의 차이를 예시와 함께 설명할 수 있으신가요?

**답변:** 추천 서비스는 클릭·시청·구매 같은 행동 데이터가 자동으로 쌓여 자연스러운 플라이휠이 형성된다. 반면 교육 Q&A 도우미는 사용자가 답변을 평가하거나 오답을 신고하도록 기능을 설계하고, 운영자가 이를 검토해야 학습용 피드백 데이터가 쌓인다.

### Chapter 4

#### 1. 세 가지 아키타입(Software 2.0, Human-in-the-loop, Autonomous) 각각에 해당하는 실제 서비스를 하나씩 떠올려 보실 수 있나요?

**답변:** Software 2.0의 예는 넷플릭스 콘텐츠 추천이다. Human-in-the-loop의 예는 AI가 초안을 만들고 상담원이 검토 후 보내는 고객 상담 시스템이다. Autonomous의 예는 정해진 안전 조건 안에서 스스로 주행 판단을 수행하는 자율주행 시스템이다.

#### 2. 하나의 제품이 처음에는 Human-in-the-loop으로 시작하여 Autonomous로 진화하는 경로를 구체적으로 그려볼 수 있으신가요? 전환의 조건은 무엇일까요?

**답변:** 학습 Q&A 도우미는 처음에는 AI 답변을 멘토가 승인·수정하는 방식으로 시작할 수 있다. 승인·수정 기록을 모아 자주 묻는 주제의 정확도와 안전 규칙을 높이고, 위험이 낮은 범위부터 자동 답변으로 전환한다. 전환 조건은 충분한 품질 검증, 낮은 오답 피해, 예외 처리·신고·롤백 체계의 준비다.

#### 3. 자신이 만들고 싶은 ML 제품은 어떤 아키타입에 해당하며, 그에 따라 모델 정확도·실패 비용·데이터 플라이휠 전략이 어떻게 달라지는지 정리해 보셨나요?

**답변:** 초기 학습 Q&A 도우미는 Human-in-the-loop이 적합하다. 학습 조언의 오답은 잘못된 학습 방향으로 이어질 수 있으므로, 높은 신뢰도가 필요한 질문은 사람 검토나 출처 제시를 사용한다. 답변 평가·수정·신고를 저장해 지식베이스와 평가셋을 개선하는 플라이휠을 설계한다.

### Chapter 5

#### 1. ML 프로젝트에 필요한 5가지 역할을 나열하고, "풀스택 ML 엔지니어"가 이 중 어디까지 커버할 수 있는지 설명할 수 있으신가요?

**답변:** 필요한 역할은 ML/Applied 엔지니어, 데이터 엔지니어, ML 플랫폼 엔지니어, 프로덕트 매니저, 도메인 전문가다. 풀스택 ML 엔지니어는 초기 단계에서 모델 개발·간단한 데이터 파이프라인·API 배포까지 넓게 맡을 수 있다. 하지만 대규모 데이터 운영, 제품 우선순위 결정, 전문 도메인 검증은 각 역할과 협업해야 한다.

#### 2. "리서치와 프로덕션의 거리를 좁혀라"는 원칙이 구체적으로 팀의 일하는 방식에 어떤 변화를 요구하는지 생각해 보셨나요?

**답변:** 연구 단계부터 실제 입력 형식, 지연 시간, 비용, 장애 상황, 평가 기준을 함께 고려해야 한다. 실험 코드는 데이터·모델 버전과 함께 기록하고, 작은 API와 사용자 피드백으로 빠르게 검증한다. 연구자와 제품·인프라 담당자가 공통 지표를 보며 짧은 반복 주기로 협업하는 방식이 필요하다.

### Chapter 6

#### 1. 프로젝트 시작 전 필수 질문 10가지 중, 자신의 프로젝트에서 가장 답하기 어려운 3개는 무엇이며 왜 어려운지 정리해 보셨나요?

**답변:** 첫째, 사용자가 실제로 원하는 답변 품질 기준은 개인차가 커서 정의하기 어렵다. 둘째, 어떤 피드백을 정답 데이터로 인정할지는 멘토·학습자 평가가 다를 수 있어 어렵다. 셋째, 서비스 비용 대비 효과는 초기 사용자 수와 사용 빈도가 불확실해 예측하기 어렵다. 따라서 PoC에서 대표 질문, 출처 정확성, 사용자 만족도, 1회 답변 비용을 함께 측정한다.

#### 2. 고임팩트 프로젝트를 찾는 4가지 멘탈 모델(예측 비용 하락, 마찰 감소, Software 2.0, 업계 벤치마킹)을 자신의 도메인에 각각 적용해 보실 수 있나요?

**답변:** 예측 비용 하락은 멘토에게 반복 질문을 받는 시간을 줄이는 데 적용할 수 있다. 마찰 감소는 여러 문서에서 답을 찾는 과정을 한 번의 질문으로 줄이는 것이다. Software 2.0은 고정 규칙 대신 질문·문서·평가 데이터로 답변 품질을 개선하는 방식이다. 업계 벤치마킹은 교육 플랫폼의 AI 튜터·검색 기능을 비교해 최소 기능과 차별점을 정하는 데 활용한다.

#### 3. "정확도에 9를 하나 더 추가하면 비용이 10배 증가한다"는 법칙이 자신의 프로젝트에 어떤 의미를 갖는지 생각해 보셨나요? 요구 정확도를 낮출 수 있는 제품 설계 방법은 없을까요?

**답변:** 모든 질문에 완벽한 답을 요구하면 고품질 라벨, 큰 모델, 사람 검수 비용이 급격히 늘어난다. 출처와 확신 수준을 표시하고, 모르는 질문에는 답변을 보류해 멘토에게 연결하며, 저위험 FAQ부터 자동화하면 필요한 정확도와 실패 비용을 낮출 수 있다.

#### 4. "당신은 구글이 아니다"라는 원칙에 비추어, 자신의 프로젝트에서 지금 당장 필요한 도구와 나중에 도입해도 되는 도구를 구분할 수 있으신가요?

**답변:** 지금은 문서 저장소, 간단한 RAG 파이프라인, LLM API, FastAPI, 기본 로그와 평가셋이면 충분하다. 대규모 Kubernetes, 복잡한 피처 스토어, 자체 파운데이션 모델 학습, 다중 리전 인프라는 실제 사용자·트래픽·반복 학습 요구가 확인된 뒤에 도입한다.

## 통합 체크포인트

### 1. **파이프라인 위치 인식**: "모델 배포 → Full Stack DL → MLOps"라는 3단계 학습 경로에서, 오늘 다룬 내용이 왜 모델 배포 직후이자 MLOps 직전에 위치해야 하는지를 자신의 언어로 설명할 수 있으신가요?

**답변:** 모델 배포를 통해 모델을 호출하는 방법을 익힌 뒤에는, 무엇을 누구에게 어떤 기준으로 제공할지 제품 관점이 필요하다. Full Stack DL은 이 문제 정의와 데이터·사용자 피드백의 연결을 다룬다. 그 설계가 있어야 이후 MLOps에서 자동화할 파이프라인, 품질 지표, 모니터링 대상이 명확해진다.

### 2. **종합 기획**: 관심 있는 ML 프로젝트 하나를 선택하여, 오늘 배운 프레임워크를 순서대로 적용해 보세요. (1) ML이 정말 필요한가? → (2) Build/Buy/API 중 무엇? → (3) 아키타입은? → (4) 실현 가능성 × 임팩트는? → (5) 비용의 3대 동인은? → (6) PoC 종료 조건은?

**답변:** (1) 문서량이 많고 질문 표현이 다양해 단순 FAQ만으로는 부족하므로 ML이 필요하다. (2) 초기에는 LLM API와 RAG를 사용한다. (3) 초기 아키타입은 Human-in-the-loop이다. (4) 실현 가능성과 임팩트가 모두 비교적 높다. (5) 비용은 문서·평가 데이터 준비, LLM 호출·인프라, 사람 검토 시간의 영향을 받는다. (6) 대표 질문 세트에서 출처가 있는 유용한 답변 비율, 사용자 만족도, 답변당 비용이 사전에 정한 기준을 만족하면 PoC를 종료하고 다음 단계로 진행한다.

### 3. **둥근 지구 설계**: 위에서 선택한 프로젝트의 데이터 플라이휠을 구체적으로 그려 보세요. 사용자의 어떤 행동이 데이터가 되고, 그 데이터가 어떻게 모델을 개선하며, 개선된 모델이 어떻게 더 많은 사용자를 끌어들이나요?

**답변:** 사용자의 질문, 선택한 문서, 답변 평가, 재질문, 오답 신고가 데이터가 된다. 운영자는 개인정보를 제외한 피드백을 검토해 문서를 보완하고 검색·프롬프트·평가셋을 개선한다. 개선된 답변은 탐색 시간과 오답을 줄여 사용 만족도를 높이고, 더 많은 사용과 피드백으로 이어진다.

### 4. **실패 시나리오**: 위 프로젝트가 실패한다면 가장 가능성 높은 원인은 무엇일까요? 기술적 비실현성, 프로덕션 전환 실패, 조직 공감대 부족, 작은 문제 해결 중 어디에 해당하며, 이를 사전에 방지하기 위해 기획 단계에서 무엇을 할 수 있을까요?

**답변:** 가장 가능성 높은 원인은 작은 문제 해결, 즉 사용자가 이미 더 빠른 방식으로 답을 얻거나 도우미의 답변을 신뢰하지 않는 경우다. 기획 단계에서 실제 학습자 인터뷰와 대표 과제 관찰을 통해 반복적으로 발생하는 불편을 확인하고, 시간 절감·정확성·재사용률을 성공 지표로 정한다. 작은 사용자 그룹 PoC로 가치를 먼저 검증한다.

### 5. **기술적 부채 예측**: 이 프로젝트가 성공적으로 배포된 후 6개월 뒤, 어떤 종류의 기술적 부채가 쌓여 있을 것으로 예상되시나요? CACE, 데이터 드리프트, 외부 세계의 불안정성 중 어떤 것이 가장 위협적일까요?

**답변:** 가장 위협적인 것은 데이터 드리프트다. 학습 자료와 커리큘럼이 바뀌고 새 질문 유형이 생기면 기존 문서와 평가셋이 빠르게 낡을 수 있다. 동시에 LLM API의 모델·가격·정책 변경도 외부 세계의 불안정성이다. 문서와 데이터 버전 관리, 정기 평가, 변경 감지, 대체 모델·API 계획을 미리 마련해야 한다.
