# FSDL Day 3 - 모델 테스트·트러블슈팅·성능 최적화

## 체크포인트 답변

### Chapter 13

#### 1. ML 테스트가 "다크 소울"이라 불리는 이유를 전통 소프트웨어와 비교하여 3가지 관점에서 설명할 수 있으신가요?

**답변:** 첫째, 전통 소프트웨어는 정해진 입력에 대한 정답 출력을 비교하기 쉽지만, ML은 확률적 예측을 하므로 모든 입력의 정답을 미리 알기 어렵다. 둘째, 코드뿐 아니라 학습 데이터, 라벨, 전처리, 난수, 모델 가중치가 결과에 영향을 주므로 실패 원인을 분리하기 어렵다. 셋째, 데이터 분포와 사용자 행동이 바뀌면 코드가 변하지 않아도 성능이 저하될 수 있어, 배포 후에도 테스트와 모니터링이 필요하다.

#### 2. 테스트 수트를 "분류기"로 보았을 때, 오탐(False Alarm)이 왜 위험한지 실제 사례를 들어 설명할 수 있으신가요?

**답변:** 테스트 수트는 커밋을 정상과 버그로 분류하는 분류기다. 오탐은 정상적인 변경을 버그라고 잘못 판단해 테스트를 실패시키는 경우다. 예를 들어 데이터 분포의 자연스러운 계절 변화를 지나치게 좁은 평균 범위로 검사하면, 정상 데이터도 실패 처리된다. 개발자가 코드 문제를 찾는 대신 테스트 임계값을 무조건 완화하거나 테스트를 삭제하는 습관이 생기면, 실제 버그를 잡는 테스트의 신뢰성도 사라진다.

#### 3. 암기 테스트(`overfit_batches=1`)가 실패했을 때 의심해야 할 원인 5가지를 나열하고, 각각의 디버깅 방법을 떠올릴 수 있으신가요?

**답변:**

1. 입력과 라벨의 짝이 어긋났을 수 있다. 한 배치의 입력·라벨을 직접 출력해 순서, shape, dtype을 확인한다.
2. 전처리나 토크나이징이 잘못되었을 수 있다. 전처리 전후 샘플을 비교하고, 입력이 모두 같은 값이나 빈 값이 되지 않았는지 확인한다.
3. 모델 출력 차원, 라벨 범위, loss 함수 조합이 맞지 않을 수 있다. logits shape, 클래스 수, 라벨의 최솟값·최댓값을 확인한다.
4. gradient가 끊기거나 optimizer에 학습할 파라미터가 빠졌을 수 있다. `requires_grad`, gradient 값, optimizer의 parameter group을 확인한다.
5. 암기를 방해하는 설정이 남아 있을 수 있다. Dropout·강한 augmentation·weight decay를 줄이거나 끄고, 학습률과 epoch 수를 늘려 한 배치에만 충분히 학습시킨다.

#### 4. 데이터 기댓값 테스트에서 "느슨한 경계" 원칙이 왜 중요한지, 경계를 너무 엄격하게 잡으면 어떤 문제가 발생하는지 설명해 보세요.

**답변:** 기댓값 테스트의 목적은 정상적인 변동을 막는 것이 아니라 데이터 파이프라인의 명백한 이상을 빠르게 찾는 것이다. 평균, 길이, 클래스 비율 등에 너무 정확한 경계를 적용하면 작은 계절성 변화나 데이터 증가처럼 정상적인 변화도 실패한다. 그 결과 오탐이 늘고, 팀은 경고를 무시하거나 테스트를 끄게 된다. 따라서 처음에는 빈 데이터, 필수 컬럼 누락, 불가능한 값처럼 확실한 오류를 잡는 넓은 범위의 스모크 테스트부터 둔다.

#### 5. 행동 테스트의 "불변성 테스트"와 "방향성 테스트"의 차이를 자신의 프로젝트에 적용하여 각각 1개씩 예시를 만들어 보실 수 있나요?

**답변:** 불변성 테스트는 의미를 바꾸지 않는 입력 변화 뒤에도 예측이 유지되는지 확인한다. 학습 Q&A 도우미에서는 “Docker 설치 방법 알려줘”와 “Docker 설치 방법 알려줘!”처럼 문장 부호만 달라진 질문에 같은 문서·유사한 답변이 나와야 한다. 방향성 테스트는 입력의 의미를 바꾸면 출력이 기대 방향으로 바뀌는지 확인한다. 예를 들어 “FastAPI 서버를 실행하는 방법”보다 “FastAPI 서버 실행 오류를 해결하는 방법”이라는 질문에서는 오류 해결 문서의 검색 점수나 답변의 트러블슈팅 비중이 높아져야 한다.

### Chapter 14

#### 1. "Make it Run → Make it Fast → Make it Right" 순서에서, 왜 ML에서는 "Fast"가 "Right"보다 먼저 와야 하는지 설명할 수 있으신가요?

**답변:** ML 성능 개선은 여러 가설을 반복 실험해 검증하는 과정이다. 실험이 너무 느리면 하루에 시도할 수 있는 횟수가 줄어들고, 데이터·모델·학습률 중 무엇이 문제인지 확인하는 속도도 느려진다. 따라서 먼저 파이프라인을 정상 실행하고 병목을 줄여 빠른 피드백 주기를 만든 뒤, 그 위에서 성능을 체계적으로 개선해야 한다.

#### 2. OOM 오류를 해결하는 4단계 전략을 순서대로 말할 수 있으신가요? Adam이 파라미터의 3~4배 메모리를 쓰는 이유는 무엇인가요?

**답변:** 첫째 혼합 정밀도(`16-mixed`)를 사용한다. 둘째 물리적 batch size를 줄인다. 셋째 gradient accumulation으로 작은 배치를 여러 번 누적해 큰 유효 배치 크기를 유지한다. 넷째 gradient checkpointing으로 중간 활성값을 저장하는 대신 필요할 때 재계산한다. Adam은 모델 파라미터 외에도 gradient와 1차·2차 모멘트 상태를 보관하므로, 파라미터 자체보다 훨씬 많은 메모리를 사용할 수 있다.

#### 3. 프로파일링 결과에서 `get_train_batch`가 전체 시간의 60%를 차지한다면, 어떤 최적화를 우선 시도하시겠어요? 반대로 `training_step`이 90%라면요?

**답변:** `get_train_batch`가 느리면 데이터 로딩이 병목이므로 데이터 캐싱, 효율적인 전처리·토크나이징, 적절한 `num_workers`, `pin_memory`, `persistent_workers`, 빠른 저장소 사용을 먼저 측정하며 조정한다. `training_step`이 90%라면 모델 연산이 병목이므로 GPU 사용 여부, mixed precision, batch size, 모델 크기·sequence length, 연산 효율을 점검한다. 두 경우 모두 실제 프로파일링 결과를 기준으로 한 번에 하나씩 바꿔 효과를 비교한다.

#### 4. 스케일링 법칙의 "작은 실험 → 직선 외삽 → 필요 자원 추산" 흐름을 자신의 언어로 설명하고, 이것이 비즈니스적으로 어떤 가치를 주는지 설명해 보세요.

**답변:** 먼저 작은 데이터·작은 모델·짧은 학습 시간으로 여러 실험을 해 성능이 자원 규모에 따라 어떻게 변하는지 측정한다. 그 추세를 바탕으로 더 큰 데이터나 모델에서 기대할 성능과 필요한 GPU 시간·비용을 추정한다. 이를 통해 큰 비용을 먼저 쓰기 전에 목표 성능 달성 가능성을 판단하고, 투자 예산·일정·중단 기준을 근거 있게 정할 수 있다.

#### 5. 성능 저하 진단표(오버피팅/언더피팅/분포 변화)에서, 자신의 최근 프로젝트가 어떤 상황이었는지 분석하고 적절한 처방을 매칭해 보세요.

**답변:** 최근 Iris 분류 실습은 작고 정제된 데이터셋으로 학습했기 때문에, 실제 운영 입력을 붙인다면 학습 데이터와 다른 값 범위가 들어오는 분포 변화가 가장 현실적인 위험이다. 이때는 요청 입력의 범위·결측·형식을 검증하고, 실제 입력과 학습 데이터 분포를 비교하며, 필요한 경우 새 데이터를 수집해 재학습해야 한다. 학습 F1만 높고 검증 성능이 낮다면 오버피팅으로 보고 규제·데이터 확장·교차 검증을 고려하며, 둘 다 낮다면 언더피팅으로 보고 데이터 표현·모델 용량·학습 설정을 점검한다.

### Chapter 15

#### 1. LLM 기반 시스템을 Accuracy만으로 평가할 수 없는 이유를 설명하고, 추가로 필요한 평가 차원을 5가지 나열할 수 있으신가요?

**답변:** LLM의 답변은 하나의 정답 라벨로 고정하기 어렵고, 같은 질문에도 여러 좋은 답이 가능하다. 또한 표면적으로 맞아 보여도 근거 없이 만든 내용이 섞일 수 있다. 따라서 정확성 외에 충실성(Faithfulness), 완전성(Completeness), 관련성(Relevance), 유창성(Fluency), 안전성(Safety)을 평가해야 한다. RAG 시스템에서는 검색 문서 인용의 정확성도 별도 차원으로 확인한다.

#### 2. LLM-as-a-Judge의 장점과 주의할 한계(편향)를 각각 설명하고, 편향을 완화하는 방법을 하나 제안해 보세요.

**답변:** LLM-as-a-Judge는 사람 평가보다 빠르게 많은 사례를 일관된 기준으로 채점할 수 있어 반복 실험과 회귀 테스트에 유리하다. 반면 평가 모델도 길이가 긴 답변을 선호하거나, 자신의 스타일과 유사한 답변을 높게 평가하는 편향을 가질 수 있다. 이를 완화하려면 사람이 검토한 골든 세트로 평가 결과를 주기적으로 교정하고, 평가 프롬프트에 길이보다 사실성·핵심 충족 여부를 우선하라고 명시한다.

#### 3. 입력 드리프트, 출력 드리프트, 성능 드리프트의 차이를 각각 한 문장으로 설명하고, 자신의 프로젝트에서 가장 가능성 높은 드리프트 유형은 무엇인지 분석해 보세요.

**답변:** 입력 드리프트는 서비스에 들어오는 질문·피처의 분포가 학습 시점과 달라지는 현상이다. 출력 드리프트는 모델이 내놓는 클래스·답변·점수의 분포가 비정상적으로 변하는 현상이다. 성능 드리프트는 실제 정답이나 사용자 피드백 기준 품질이 떨어지는 현상이다. 학습 Q&A 도우미에서는 커리큘럼, 실습 환경, 라이브러리 버전이 바뀌어 새 질문 유형이 생길 수 있으므로 입력 드리프트가 가장 먼저 나타날 가능성이 높다.

#### 4. "모델은 시간이 지나면 썩는다"는 말의 의미를 코로나19 같은 구체적 사례로 설명할 수 있으신가요? 이를 방지하기 위해 어떤 시스템이 필요한가요?

**답변:** 모델은 학습 시점의 세계를 기준으로 패턴을 배웠기 때문에, 환경이 크게 변하면 같은 코드와 가중치라도 예측 품질이 낮아질 수 있다. 예를 들어 코로나19 이후 이동·구매·예약 행동이 급격히 달라지면 이전 데이터로 학습한 수요 예측 모델은 잘못된 예측을 할 수 있다. 이를 줄이려면 입력·출력 분포와 실제 성능을 지속적으로 모니터링하고, 임계값 초과 시 알림·원인 분석·평가셋 갱신·재학습·안전한 재배포로 이어지는 운영 체계가 필요하다.
