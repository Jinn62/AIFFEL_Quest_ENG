### Chapter 7

#### 1. VS Code의 원격 개발 기능이 ML 엔지니어에게 왜 필수적인지, GPU 서버 활용 관점에서 설명할 수 있으신가요?

**답변:** 대용량 데이터와 GPU가 있는 원격 서버에서 코드 실행·디버깅을 수행하면서도, 로컬 VS Code와 같은 편집·검색·Git 기능을 사용할 수 있기 때문이다. 데이터와 모델을 로컬로 복사하지 않아도 되므로 전송 시간과 환경 차이를 줄이고, 고사양 서버 자원을 효율적으로 활용할 수 있다.

#### 2. 주피터 노트북의 세 가지 문제점(실행 순서, 리팩토링, 버전 관리)을 각각 어떻게 해결하는지 "하이브리드 솔루션"의 관점에서 설명해 보세요.

**답변:** 실행 순서 문제는 핵심 로직을 위에서 아래로 실행되는 `.py` 모듈과 스크립트로 옮겨 해결한다. 리팩토링은 VS Code에서 모듈의 함수·클래스를 관리해 이름 변경과 테스트를 적용하여 해결한다. 버전 관리는 출력이 섞인 노트북 대신 소스 코드와 설정 파일을 Git으로 관리하여 해결한다. 노트북은 탐색·시각화에만 사용하고 `%autoreload`로 모듈 변경을 반영하는 것이 하이브리드 방식이다.

#### 3. "결정적 빌드"가 보장되지 않았을 때, 팀 협업에서 어떤 문제가 발생하는지 경험이나 예시를 떠올려 보실 수 있나요?

**답변:** 같은 `pip install` 명령이라도 실행 시점에 따라 다른 라이브러리 버전이 설치되어, 한 사람은 모델을 학습하거나 API를 실행할 수 있지만 다른 사람은 오류가 나거나 다른 결과를 얻을 수 있다. Docker 이미지나 버전이 고정된 requirements 파일이 없으면 원인을 코드·데이터·환경 중 어디에서 찾아야 할지 알기 어렵고 재현도 불가능해진다.

#### 4. `requirements.in`과 `requirements.txt`의 역할 차이를 설명할 수 있으신가요?

**답변:** `requirements.in`에는 프로젝트가 직접 선택한 상위 의존성만 간단히 기록한다. `requirements.txt`에는 그 의존성과 하위 의존성의 정확한 버전을 모두 고정해 실제 설치 환경을 재현한다. 따라서 전자는 사람이 의도를 관리하는 파일이고, 후자는 결정적 빌드를 위한 설치 기준 파일이다.

### Chapter 8

#### 1. 전통적인 PyTorch 학습 루프 대비 Lightning으로 전환했을 때 사라지는 코드(직접 안 써도 되는 것) 5가지를 나열할 수 있으신가요?

**답변:** 옵티마이저의 `zero_grad`, 역전파 `loss.backward`, 파라미터 갱신 `optimizer.step`, GPU 장치 이동 코드, 학습·검증 반복 루프를 직접 작성할 필요가 줄어든다. 이 밖에도 체크포인트 저장, 로그 기록, 다중 GPU 설정을 Trainer와 Callback 설정으로 처리할 수 있다.

#### 2. `LightningDataModule`의 `setup` 메서드와 `train_dataloader` 메서드의 역할 차이를 설명할 수 있으신가요? 왜 데이터 분할과 DataLoader 생성을 분리하는 것이 중요한가요?

**답변:** `setup`은 원본 데이터를 내려받거나 읽고 train·validation·test 데이터셋으로 분할하는 단계다. `train_dataloader`는 이미 준비된 train 데이터셋을 배치 크기, 셔플, 워커 수 등의 설정으로 DataLoader에 감싸 반환한다. 두 역할을 분리하면 데이터 분할 기준이 흔들리지 않고, 같은 데이터셋을 학습·검증·테스트에서 재사용하며, 실행 환경에 따라 로더 설정만 바꾸기 쉬워진다.

#### 3. 이 장에서 배운 `_shared_step` 패턴을 자신의 프로젝트에 적용한다면, 공통 로직과 각 단계(학습/검증/테스트)에서 달라지는 부분은 각각 무엇인가요?

**답변:** RAG 답변 품질 평가 모델이라면 입력 배치 처리, 모델 순전파, 손실 계산, 예측 생성은 `_shared_step`에 둔다. 학습 단계는 손실로 가중치를 갱신하고, 검증 단계는 하이퍼파라미터 선택과 Early Stopping의 기준이 될 지표를 기록한다. 테스트 단계는 최종 고정 평가셋에서 정확도·근거 문서 일치도 같은 최종 성능을 보고한다.

#### 4. `overfit_batches=1` 테스트가 실패했을 때 의심해야 할 원인 3가지와, 각각의 디버깅 방법을 설명할 수 있으신가요?

**답변:** 첫째, 입력과 라벨의 매칭 또는 데이터 전처리가 잘못되었을 수 있으므로 한 배치의 shape, dtype, 라벨 값을 출력해 확인한다. 둘째, 손실 함수·출력 차원·라벨 범위가 맞지 않을 수 있으므로 모델 출력과 loss 입력을 비교한다. 셋째, 옵티마이저에 학습 대상 파라미터가 빠졌거나 gradient가 끊겼을 수 있으므로 `requires_grad`, gradient 값, optimizer 파라미터 목록을 확인한다.

#### 5. 8.13의 전체 코드를 여러분의 실제 프로젝트에 맞게 수정한다면, `LitClassifier.__init__`과 `MyDataModule.setup`에서 각각 무엇을 바꿔야 하는지 구체적으로 떠올려 보세요.

**답변:** `LitClassifier.__init__`에서는 사용할 사전학습 임베딩·분류 모델, 출력 클래스 수, learning rate, loss 함수와 평가 지표를 프로젝트에 맞게 바꾼다. `MyDataModule.setup`에서는 질문·문서·정답 또는 평가 라벨을 읽는 위치, train·validation·test 분할 기준, 토크나이징·길이 제한·배치 구성을 바꾼다.

### Chapter 9

#### 1. GPU 선택의 3대 지표(메모리 대역폭, 연산 속도, 인터커넥트) 중 분산 학습에서 가장 중요한 것은 무엇이며, 그 이유를 "고속도로와 톨게이트" 비유로 설명할 수 있으신가요?

**답변:** 여러 GPU가 함께 학습할 때는 인터커넥트가 특히 중요하다. 각 GPU가 계산한 gradient를 자주 주고받아야 하는데, GPU 사이 연결이 느리면 넓은 고속도로에 진입했어도 좁은 톨게이트에서 차량이 막히는 것처럼 GPU가 통신을 기다리게 된다. NVLink 같은 빠른 연결은 이 병목을 줄인다.

#### 2. "시간당 비용"이 아니라 "실험당 비용"으로 GPU를 평가해야 하는 이유를 표의 숫자 예시를 활용하여 설명할 수 있으신가요?

**답변:** 예를 들어 시간당 1달러 GPU가 10시간 걸리면 실험당 10달러이고, 시간당 4달러 GPU가 2시간 걸리면 실험당 8달러다. 후자가 시간당 가격은 높지만 총비용은 낮고 결과도 더 빨리 얻는다. 따라서 학습 시간, 실패·재실행 가능성, 개발자 대기 시간을 함께 고려해야 한다.

#### 3. 스팟 인스턴스를 안전하게 사용하기 위해 반드시 갖춰야 할 전제 조건은 무엇인가요?

**답변:** 언제든 인스턴스가 회수될 수 있으므로 모델 가중치뿐 아니라 옵티마이저·스케줄러·epoch 상태까지 주기적으로 저장하는 자동 체크포인트가 필요하다. 체크포인트는 인스턴스와 분리된 영구 저장소에 저장하고, 중단 시 마지막 체크포인트에서 재개되는지 사전에 시험해야 한다.

#### 4. 여러분이 실습에서 진행한 실험 중, W&B가 있었다면 어떤 점이 편리했을지 구체적으로 떠올려 보실 수 있나요?

**답변:** Iris 모델이나 이후 RAG 평가 실험에서 모델 종류, learning rate, 데이터 버전, 정확도, loss, 실행 시간과 환경을 한 화면에 기록할 수 있다. 어떤 설정이 가장 좋았는지 비교하고, 동료가 같은 결과를 재현하거나 성능 저하 원인을 추적하기 쉬워진다.

### Chapter 10

#### 1. 스토리지 계층 구조의 지연 시간 차이가 `DataLoader`의 `num_workers` 설정에 어떤 영향을 미치는지 설명할 수 있으신가요?

**답변:** 원격 객체 저장소나 느린 디스크에서 데이터를 읽을수록 I/O 대기 시간이 길어져 GPU가 빈 배치를 기다릴 수 있다. 이때 `num_workers`를 늘리면 여러 프로세스가 미리 데이터를 읽고 전처리해 대기 시간을 숨길 수 있다. 다만 너무 많이 늘리면 CPU·메모리·파일 핸들 경쟁이 생기므로 실제 처리량을 측정해 적절한 값을 정해야 한다.

#### 2. "이진 데이터는 S3에, URL만 DB에"라는 원칙의 이유를 설명할 수 있으신가요? 이 원칙을 어겼을 때 어떤 문제가 발생하나요?

**답변:** 이미지·오디오·모델 파일 같은 큰 이진 데이터는 확장성과 비용에 유리한 객체 저장소에 두고, 파일 위치·라벨·생성 시각 같은 작은 메타데이터만 DB에서 빠르게 검색하는 것이 효율적이다. 큰 파일을 DB에 직접 넣으면 DB 백업과 복제가 무거워지고 쿼리 성능·운영 비용이 악화된다.

#### 3. OLTP와 OLAP의 차이를 "행 지향 vs 열 지향"의 관점에서, 각각 어떤 쿼리에 적합한지 예시와 함께 설명할 수 있으신가요?

**답변:** OLTP는 행 지향 저장으로 사용자 한 명의 질문 이력 조회나 새 피드백 저장처럼 특정 레코드를 빠르게 읽고 쓰는 작업에 적합하다. OLAP는 열 지향 저장으로 한 달간 질문 유형별 평균 만족도처럼 일부 컬럼을 대량 집계하는 분석 작업에 적합하다.

### Chapter 11

#### 1. 레이블링을 최소화하는 4가지 전략(자기주도 학습, 증강, 합성 데이터, 사용자 피드백)을 각각 한 문장으로 요약하고, 자신의 프로젝트에 적용 가능한 것을 골라보실 수 있나요?

**답변:** 자기주도 학습은 라벨 없이 데이터 자체의 구조를 학습하는 방식이다. 증강은 의미를 유지한 변형으로 학습 데이터를 늘리는 방식이다. 합성 데이터는 생성 모델로 정답이 포함된 예시를 만드는 방식이다. 사용자 피드백은 클릭·평가·수정 같은 행동을 라벨로 전환하는 방식이다. 학습 Q&A 도우미에는 문서 기반 질의응답 합성 데이터와 사용자의 답변 평가·수정 피드백을 우선 적용할 수 있다.

#### 2. 수동 레이블링의 5단계 프로세스 중 "골드 표준 데이터셋"은 왜 필요한가요? 이것 없이 외주를 맡기면 어떤 문제가 생기나요?

**답변:** 골드 표준 데이터셋은 도메인을 이해한 담당자가 만든 신뢰할 수 있는 기준 답안으로, 라벨러 결과의 정확성과 일관성을 측정하는 기준이다. 이것 없이 외주를 맡기면 모호한 사례에서 라벨러마다 판단 기준이 달라져도 품질을 측정할 방법이 없고, 잘못된 데이터로 모델을 학습시킬 위험이 있다.

#### 3. 약지도 학습이 수동 레이블링 대비 갖는 가장 큰 장점을 "유지보수" 관점에서 설명해 보세요. 레이블 체계가 변경되었을 때 각각 어떤 일이 벌어지나요?

**답변:** 약지도 학습은 규칙을 코드로 관리하므로 레이블 체계가 바뀌면 레이블링 함수만 수정해 전체 데이터에 다시 적용할 수 있다. 수동 레이블링은 기존 데이터를 다시 사람에게 맡겨야 하므로 시간·비용이 크고 기준 일관성도 다시 검증해야 한다.

#### 4. LLM을 이용한 합성 데이터 생성이 효과적인 상황과 주의해야 할 점은 무엇인가요?

**답변:** 실제 라벨 데이터가 부족하지만 태스크의 입력·출력 형식과 좋은 답변 기준을 비교적 명확히 정의할 수 있을 때 효과적이다. 다만 LLM이 만든 사실 오류, 편향, 반복 표현이 대량으로 섞일 수 있으므로 소량의 사람 검토, 중복 제거, 실제 사용자 데이터와의 분포 비교, 평가셋 분리를 반드시 해야 한다.

### Chapter 12

#### 1. 데이터 버전 관리의 4단계 중 자신의 현재 프로젝트는 어느 레벨에 해당하나요? 한 단계 올리려면 구체적으로 무엇을 해야 하나요?

**답변:** 현재 실습은 코드와 `model.joblib`은 남아 있지만 학습에 사용한 데이터·전처리·실행 조건을 체계적으로 기록하지 않았으므로 Level 0~1 사이에 가깝다. 한 단계 올리려면 데이터 파일 또는 데이터 URL·라벨 목록을 날짜와 버전으로 보관하고, 학습에 사용한 데이터 버전·코드 커밋·패키지 버전을 함께 기록해야 한다.

#### 2. "코드 + 데이터 = 모델"이라는 공식에서, 데이터 버전 관리 없이 모델을 롤백하려 할 때 어떤 문제가 발생하는지 구체적인 시나리오를 그려보실 수 있나요?

**답변:** 지난주 코드로 되돌렸는데도 답변 품질이 회복되지 않을 수 있다. 그 사이 문서 청크 분할 방식이나 라벨 목록이 바뀌었고, 지난주 데이터셋을 복원할 수 없기 때문이다. 결국 어떤 코드와 어떤 데이터 조합이 좋은 모델을 만들었는지 검증하지 못하며, 잘못된 모델을 계속 서비스할 수 있다.

#### 3. Level 2("코드로서의 데이터")의 "장부" 비유를 자신의 언어로 다시 설명할 수 있으신가요?

**답변:** 실제 대용량 파일을 Git에 모두 넣는 대신, 각 파일의 저장 위치·해시·라벨·분할 정보를 적은 작은 목록 파일을 Git으로 관리하는 방식이다. 이 목록 파일은 데이터셋의 장부 역할을 하므로 특정 커밋으로 돌아가면 그 시점에 사용한 데이터 조합을 다시 구성할 수 있다.

#### 4. 워크플로우 자동화가 필요해지는 시점은 언제인가요? "단순한 파이썬 스크립트"로 충분한 경우와, Airflow 같은 전문 도구가 필요한 경우를 구분할 수 있으신가요?

**답변:** 데이터 수집·정제·평가·학습·배포가 반복되고, 단계별 의존성·실패 재시도·일정 실행·상태 추적이 필요해지면 전문 자동화 도구가 필요하다. 한 사람이 가끔 실행하는 단일 데이터 변환이나 작은 학습은 설정 비용이 적은 Python 스크립트와 cron으로 충분하다. 여러 작업이 매일 연결되고 실패한 단계만 다시 실행해야 할 때 Airflow 같은 도구를 고려한다.

## Day 2 통합 체크포인트

### 1. **환경 점검**: 여러분이 지금까지 실습에 사용한 환경을 떠올려 보세요. 재현 가능한 환경 구축(결정적 빌드)이 되어 있었나요? 팀원에게 동일한 환경을 전달하려면 어떤 파일들이 필요한가요?

**답변:** WSL Ubuntu에서 Docker 이미지를 빌드하고 GCP VM에서 같은 이미지를 실행했으므로 FastAPI 배포 환경은 상당 부분 재현 가능했다. 하지만 Dockerfile의 패키지 버전과 베이스 이미지 태그가 완전히 고정되어 있지 않아 완전한 결정적 빌드는 아니다. 팀원에게는 `Dockerfile`, `requirements.txt`, `main.py`, `train.py`, 학습 데이터 또는 데이터 버전 목록, 모델 파일·모델 생성 절차, `.dockerignore`, 실행 방법을 담은 README가 필요하다.

### 2. **코드 리팩토링 계획**: 지금까지 작성한 PyTorch 학습 코드 중 하나를 골라, Lightning으로 리팩토링한다면 어떤 부분이 `LightningModule`로, 어떤 부분이 `Trainer` 설정으로 분리될지 구체적으로 구상해 보세요. `training_step`, `validation_step`, `configure_optimizers` 각각에 무엇이 들어가나요?

**답변:** `LightningModule`에는 모델 정의, forward, 배치별 loss·metric 계산을 둔다. `training_step`에는 train 배치의 forward·loss·로그 기록을, `validation_step`에는 validation loss·metric 기록을 둔다. `configure_optimizers`에는 AdamW와 learning rate scheduler를 설정한다. `Trainer`에는 GPU/CPU accelerator, epoch 수, mixed precision, checkpoint callback, early stopping, logger를 둔다.

### 3. **인프라 설계**: Day 1에서 기획한 ML 프로젝트를 실행한다면, GPU는 무엇을 선택하고, 클라우드는 어디를 쓰며, 실험 관리는 어떤 도구를 사용할지 구체적으로 계획해 보세요. 예상 비용은 얼마인가요?

**답변:** RAG Q&A 도우미의 초기 PoC는 임베딩 생성·평가 중심이므로 GPU 없이 CPU 또는 저비용 T4급 GPU로 시작한다. 기존 실습 연계와 GCS·Compute Engine 활용을 위해 GCP를 선택하고, 실험 메트릭과 설정은 W&B 또는 MLflow로 기록한다. 초기에는 공개 자료·작은 평가셋을 사용해 수 시간 단위의 실험으로 제한하고, 비용은 사용한 VM·GPU 시간과 저장소 비용을 실험별로 기록해 예산 안에서 운영한다.

### 4. **데이터 전략**: 같은 프로젝트의 데이터를 어떻게 확보할 것인가요? 레이블링을 최소화하는 전략 중 적용 가능한 것은 무엇이며, 데이터 버전 관리는 어느 레벨부터 시작할 것인가요?

**답변:** 공식 학습 자료와 공개 문서를 출처·라이선스와 함께 수집하고, 이를 문서 청크와 메타데이터로 저장한다. FAQ와 문서 구조를 이용한 합성 Q&A, 학습자의 답변 평가·오답 신고를 활용해 수동 라벨링을 줄인다. 처음부터 문서 URL·해시·버전·청크 기준·평가셋 목록을 Git으로 관리하는 Level 2를 목표로 한다.

### 5. **비용 시뮬레이션**: 위 프로젝트의 학습에 필요한 GPU 시간을 대략적으로 추산하고, 클라우드 비용을 "시간당"과 "실험당" 두 관점에서 비교해 보세요. 스팟 인스턴스를 쓸 수 있는 조건이 갖춰져 있나요?

**답변:** 초기 RAG PoC는 모델을 처음부터 학습하지 않으므로 임베딩 생성과 평가를 포함해 한 실험을 약 2~4시간의 저비용 GPU 또는 CPU 작업으로 가정할 수 있다. 시간당 가격만 보면 저렴한 장비가 좋아 보이지만, 실험이 길어져 반복 횟수가 줄면 총비용과 개발 시간이 커질 수 있다. 스팟 인스턴스는 데이터·체크포인트가 GCS 같은 영구 저장소에 있고 중단 후 자동 재개를 검증했을 때 사용할 수 있으며, 현재는 그 조건을 완전히 갖추기 전까지 일반 인스턴스로 작은 실험부터 진행한다.
