# Day 5 체크포인트 정리

California Housing 데이터를 활용해 정형 데이터 주택 가격 예측 서비스를 구현하며 확인한 체크포인트와 답변이다.

## 1. 프로젝트 개요

### 1. 입력과 출력은 무엇인가?

- 입력: `MedInc`, `HouseAge`, `AveRooms`, `AveBedrms`, `Population`, `AveOccup`, `Latitude`, `Longitude`의 8개 숫자 피처
- 출력: 예측 주택 가격. 모델 내부 값은 `$100,000` 단위이며, API는 `predicted_price`와 달러 단위의 `predicted_price_usd`를 함께 반환한다.

### 2. MNIST와 비교한 데이터 형태의 차이는 무엇인가?

MNIST는 픽셀로 구성된 이미지 입력을 받아 0~9 중 하나를 고르는 분류 문제다. Day 5는 8개의 수치형 피처를 받아 연속적인 가격을 예측하는 정형 데이터 회귀 문제다. 따라서 이미지 변환 대신 수치 정규화와 피처 순서 관리가 중요하다.

### 3. 새로 만든 파일과 역할은 무엇인가?

주요 구현 파일은 다음과 같다.

- `app/housing_model.py`: `HousingModel` 정의와 모델 로드·정규화·추론을 담당하는 `HousingPredictor`
- `app/housing_schemas.py`: FastAPI 요청·응답 Pydantic 스키마와 입력 검증 규칙
- `app/housing_api.py`: `/health`, `/predict` FastAPI 엔드포인트와 비동기 추론 처리
- `frontend/app_housing.py`: 8개 수치 입력을 받아 API를 호출하고 가격을 보여 주는 Streamlit UI

저장 파일은 `models/housing_model.pth`(가중치)와 `models/housing_preprocessing.json`(평균, 표준편차, 피처 순서)이다.

## 2. 모델 준비와 전처리

### 1. 테스트 데이터에도 학습 데이터 통계를 쓰는 이유는 무엇인가?

정규화 기준은 학습 과정에서 얻은 정보로 고정해야 한다. 테스트 데이터의 평균이나 표준편차를 사용하면 평가 시점에 테스트 분포 정보를 미리 본 데이터 누수가 발생한다. 배포 환경의 새 입력도 학습 데이터에서 저장한 `mean`, `std`로 정규화해야 한다.

### 2. 모델 가중치 외에 함께 저장해야 하는 것은 무엇이며, 왜 필요한가?

`mean`, `std`, `feature_names`를 함께 저장해야 한다. 같은 모델 가중치라도 입력을 학습 때와 다른 방식으로 정규화하거나 피처 순서를 바꾸면 모델은 의미가 달라진 입력을 받아 조용히 잘못된 예측을 만든다.

### 3. 피처를 `self.feature_names` 순서로 배열하는 이유는 무엇인가?

딕셔너리는 모델 입력 순서를 보장하는 계약이 아니다. 학습할 때의 피처 순서와 추론 때의 순서가 정확히 같아야 각 입력값이 올바른 가중치와 연결된다. 따라서 `values = [features[name] for name in self.feature_names]`처럼 저장된 순서를 사용한다.

## 3. FastAPI 백엔드

### 1. `Latitude`에 `ge=32`, `le=42`를 넣은 이유는 무엇인가?

캘리포니아 주택 데이터의 유효한 지리 범위 밖 값을 API 입구에서 차단하기 위해서다. 예를 들어 위도 50은 데이터 도메인 밖이므로 모델에 전달하지 않고 FastAPI가 422 검증 오류로 응답한다.

### 2. `request.model_dump()`의 역할은 무엇인가?

Pydantic의 `HousingRequest` 객체를 일반 Python 딕셔너리로 변환한다. 변환한 `features`는 `HousingPredictor.predict()`에 전달하고, 응답의 `input_features`에도 포함한다.

### 3. `run_in_executor`가 없으면 어떤 문제가 생기는가?

PyTorch 추론은 동기적이고 CPU를 점유할 수 있다. 이를 `async` 엔드포인트에서 직접 실행하면 이벤트 루프가 막혀 다른 예측 요청이나 `/health` 요청까지 지연될 수 있다. `run_in_executor`는 추론을 별도 스레드풀로 보내 API 이벤트 루프의 블로킹을 줄인다.

## 4. Streamlit 프론트엔드

### 1. MNIST 대시보드와 입력 방식은 어떻게 다른가?

MNIST 대시보드는 이미지 업로드나 그림 입력을 전처리해 픽셀 배열로 보낸다. Day 5 대시보드는 `st.number_input()`으로 8개의 수치형 피처를 직접 받아 JSON으로 보낸다.

### 2. `min_value`, `max_value`를 설정하는 이유는 무엇인가?

사용자가 허용 범위를 벗어난 값을 입력하는 일을 UI 단계에서 줄이고, API Pydantic 검증 규칙과 일관된 입력 경험을 제공하기 위해서다. API 검증을 대체하지는 않으며, 서버에서도 같은 검증을 유지해야 한다.

### 3. `request_data`의 키가 `HousingRequest` 필드명과 일치해야 하는 이유는 무엇인가?

FastAPI는 JSON 키를 Pydantic 필드명에 대응시켜 검증한다. 이름이 다르면 필수 필드가 누락된 것으로 판단되어 422 오류가 발생하거나, 의도한 값이 모델에 전달되지 않는다.

## 5. 최종 체크포인트

### Q1. 전처리 파라미터를 모델과 함께 저장해야 하는 이유는 무엇인가?

배포에서도 학습과 동일한 정규화를 재현하기 위해서다. 가중치만 저장하면 입력 스케일이 달라져 예측의 신뢰성이 떨어진다.

### Q2. `Latitude`의 범위 제한은 왜 필요한가?

캘리포니아 밖의 비정상 입력을 모델 실행 전에 검증하고 422로 거절해, 데이터 도메인 밖의 예측을 방지하기 위해서다.

### Q3. Streamlit 입력 이름과 Pydantic 필드명이 일치해야 하는 이유는 무엇인가?

프론트엔드가 보낸 JSON을 서버가 정확히 검증·변환하고, 올바른 피처를 모델에 전달하려면 같은 키 이름을 사용해야 한다.

### Q4. `run_in_executor`를 제거하면 어떤 문제가 생길 수 있는가?

동기 추론이 FastAPI 이벤트 루프를 막아 동시 요청 처리 성능이 떨어지고, 추론 중에는 다른 요청도 늦어질 수 있다.

### Q5. MNIST 프로젝트와 Day 5 프로젝트의 가장 큰 차이는 무엇인가?

MNIST는 이미지 입력을 받아 클래스 하나를 반환하는 분류 서비스다. Day 5는 여러 수치 피처를 정규화해 연속적인 가격을 반환하는 정형 데이터 회귀 서비스다.

## 6. 회고

이번 실습에서는 모델 학습으로 끝내지 않고, 사용자가 접근할 수 있는 예측 서비스까지 연결하는 전체 과정을 경험했다. California Housing의 8개 수치형 피처를 정규화해 PyTorch 회귀 모델을 학습하고, 모델 가중치와 전처리 파라미터를 분리해 저장했다. 단일 샘플의 예측 가격과 실제 가격은 차이가 날 수 있으므로, 모델의 전체 성능은 테스트 데이터의 MAE와 같은 지표로 판단해야 한다는 점을 확인했다.
가장 중요하게 배운 점은 모델 가중치만 저장해서는 배포를 재현할 수 없다는 것이다. 학습 때 계산한 평균과 표준편차, 그리고 피처 순서를 함께 저장해야 배포 환경에서도 동일한 입력 변환을 적용할 수 있다.
FastAPI에서는 Pydantic 스키마로 잘못된 입력을 먼저 검증하고, `run_in_executor`로 동기적인 모델 추론을 별도 스레드에서 처리했다. 또한 API 기본 주소에 POST 요청을 보내면 루트 경로(`/`)의 404 오류가 발생하며, 예측 요청에는 `/predict` 엔드포인트를 지정해야 한다는 점을 디버깅 과정에서 확인했다.
다음에는 은닉층 크기, 학습 epoch, 학습률을 바꿔 MAE를 비교하며 모델 성능을 개선해 보고 싶다.
